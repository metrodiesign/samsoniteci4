# คำตัดสิน collation ของ utf8mb4 (ปิด BLK-001)

> วันที่: 2026-08-17
> สถานะ: **ตัดสินแล้ว พร้อมหลักฐาน**
> ทำซ้ำได้ด้วย: `./db/dbctl.sh collation`

## คำตัดสิน

ใช้ **`utf8mb4_general_ci`** ทุกชั้น: server, schema, table, column และ connection ของ CI4

## ทำไมเรื่องนี้ถึงต้องตัดสิน

แผนขึ้น BLK-001 ไว้ว่า *"ไม่มี safe default; ห้ามใช้ utf8mb4 โดยปล่อย collation implicit"*
และ R-15 ระบุความเสี่ยงว่าการเปลี่ยน collation ทำให้ **ข้อมูล การเรียง การค้นหา การ export
และการเปรียบเทียบเพี้ยน** ระดับวิกฤต

ระบบเดิมใช้ `utf8mb3_general_ci` คำถามคือ collation ตัวไหนของ utf8mb4 ที่ทำให้พฤติกรรม
ไม่เปลี่ยนจาก production

เพิ่มเติม: MariaDB 11.4.12 ตั้ง `character_set_collations=utf8mb4=utf8mb4_uca1400_ai_ci`
มาให้เป็นค่า default แปลว่า **ถ้าไม่ตัดสินใจ ระบบจะเลือก collation ให้เองแบบเงียบ ๆ**
และเป็นคนละตัวกับของเดิม

## วิธีพิสูจน์

ไม่ต้องยกเซิร์ฟเวอร์ MariaDB 10.6 ขึ้นมาเทียบ เพราะ:

1. `utf8mb3_general_ci` ยังมีอยู่ใน MariaDB 11.4
2. ข้อมูลทั้ง 222 MB ไม่มีอักขระ 4 ไบต์เลย ทำให้ `CONVERT(col USING utf8mb3)` ไม่สูญเสียข้อมูล

จึงเทียบ collation สองตัวบนข้อมูล production ชุดเดียวกัน ในเซิร์ฟเวอร์เดียวกันได้โดยตรง
และเทียบด้วย `WEIGHT_STRING` ซึ่งเป็นค่าที่ MariaDB ใช้ตัดสินทั้งการเรียงและการเท่ากัน
ไม่ใช่การสุ่มดูผลลัพธ์

### C2 — `utf8mb4_general_ci` เทียบกับของเดิมบน `uploadstaus` 473,152 แถว

| เกณฑ์ | ผล |
|---|---|
| แถวที่ลำดับการเรียงเปลี่ยนไป | **0** |
| ส่วนต่างของจำนวนค่าที่ถือว่าไม่ซ้ำกัน | **0** (47,718 เท่ากันทั้งสองฝั่ง) |

### C3 — ถ้าเลือก `utf8mb4_unicode_ci` แทน

| เกณฑ์ | ผล |
|---|---|
| แถวที่ลำดับการเรียงเปลี่ยนไป | **66,363** (14% ของตาราง) |
| ค่าที่หายไปเพราะถูกยุบรวม | **31** |

ตัวอย่างคู่ที่ `utf8mb4_unicode_ci` ถือว่าเป็นค่าเดียวกัน แต่ระบบเดิมแยกจากกัน:

| ค่า A | ค่า B |
|---|---|
| `4000006(น็อต)` | `4000006(น๊อต)` |
| `4000184(ออย)` | `4000184(อ้อย)` |
| `4000185(ติบ)` | `4000185(ติ๊บ)` |
| `4000187(อาชา)` | `4000187(อาช่า)` |
| `4000330(ปิมใจ)` | `4000330(ปิ่มใจ)` |
| `ซิตี้มอลล์ กรุ๊ป(เอ)` | `ซิตี้มอลล์ กรุ๊ป(เอ๋)` |

ทั้งหมดต่างกันที่วรรณยุกต์ ซึ่ง `unicode_ci` ถือว่าไม่มีน้ำหนัก ผลคือ **ชื่อลูกค้าคนละคน
ถูกนับเป็นคนเดียว** กระทบการค้นหา การนับซ้ำ และยอดรวมในรายงาน ไม่ใช่แค่ลำดับการเรียง

## ทางเลือกที่พิจารณาแล้วและเหตุผลที่ตัดทิ้ง

| ทางเลือก | เหตุผลที่ไม่เลือก |
|---|---|
| `utf8mb4_unicode_ci` | ทำลาย parity ตามผล C3 ข้างบน จัดเรียงตามหลักสากลดีกว่าก็จริง แต่แลกด้วยการยุบค่าที่ธุรกิจถือว่าต่างกัน |
| `utf8mb4_uca1400_ai_ci` | เป็น default ใหม่ของ MariaDB ที่ `accent-insensitive` ยิ่งกว่า `unicode_ci` จึงยุบวรรณยุกต์ไทยหนักกว่า และไม่มีใน `information_schema.COLLATIONS` ของอิมเมจนี้จนกว่าจะเปิดใช้ ทำให้ tooling บางตัวไม่รู้จัก |
| `utf8mb4_bin` | เทียบแบบ binary จึงเป็น case-sensitive ทั้งหมด ทำให้ login และการค้น tracking ID ที่เดิมไม่สนตัวพิมพ์ใหญ่เล็กพังทันที |
| คงไว้ที่ `utf8mb3` ไม่แปลง | ขัด target stack ที่กำหนด utf8mb4 และปิดทางรองรับอักขระ 4 ไบต์ในอนาคต |

## ผลที่ตามมาที่ต้องทำ

1. **pin ค่า default ของ charset ด้วย ไม่ใช่แค่ของ server** — `compose.yaml` ตั้ง
   `--character-set-collations=utf8mb4=utf8mb4_general_ci` เพราะ 11.4.12 map ไป
   `uca1400_ai_ci` ให้เอง ถ้าไม่ pin แล้วมี DDL หรือ literal ที่เขียน `utf8mb4` เปล่า ๆ
   จะได้ collation คนละตัวแล้วเกิด `ERROR 1267 Illegal mix of collations` (เจอจริงตอน verify)
2. **CI4 ต้องตั้ง `DBCollat=utf8mb4_general_ci` ให้ตรงกัน** (WP-01C) และทุก migration
   ที่สร้าง table ใหม่ต้องระบุ `COLLATE` ตรง ๆ ห้ามปล่อย implicit
3. คำตัดสินนี้ **ผูกกับข้อเท็จจริงว่าข้อมูลไม่มีอักขระ 4 ไบต์** ถ้าอนาคตระบบเริ่มรับ emoji
   หรืออักขระนอก BMP ต้องทดสอบซ้ำ เพราะ `general_ci` จัดการอักขระนอก BMP ต่างจาก
   collation ตระกูล UCA

## สิ่งที่คำตัดสินนี้ยังไม่ครอบ

- **ไม่ได้แก้เรื่องคอลัมน์ token/hash ที่ควรเป็น `ascii_bin`** — `tbl_users.password`,
  `tbl_reset_password.activation_id`, `ci_sessions.session_id` ยังถูกเทียบแบบไม่สนตัวพิมพ์
  ซึ่งลด entropy ของ token แต่เป็นพฤติกรรมเดิมของ production การแก้ต้องมาพร้อม
  regression test ของ login และ reset password
- ยังไม่ได้ทดสอบ parity ระดับแอป (หน้าค้นหา รายงาน export Excel) เพราะยังไม่มี CI3
  รันบน DB ตัวนี้ — อยู่ใน WP-00K/WP-00M
